# PDF Parity Architecture

PDFは「エディタ画面をページ窓で切り出したもの」です。それ以外の作り方を禁止します。

このドキュメントは `architecture.md` の旧方針「4. Editing DOM And Print DOM Are Different」を置き換えます。

## なぜ方針を変えたか

旧方針は、印刷専用のrendererを別に持ち、用紙・余白・分割禁止などを印刷側で制御する、というものでした。これはエディタが紙面WYSIWYGではなかった時代の前提です。

現在のエディタは、用紙実寸の `.a4-page-sheet` を並べ、本文を連続キャンバス上に配置し、ページ割りを実測で確定させています。つまり**エディタ自身がすでに完全な紙面レイアウトを持っています**。この状態で印刷用に第2のレイアウトを組むと、同じ問題を2回別々に解くことになり、両者は必ず乖離します。

実際に乖離していた箇所（改革前）:

| # | 内容 |
|---|---|
| D1 | ユニット構築が2系統。問題エリアの表示条件が編集側と印刷側で違う |
| D2 | ページ割りが3系統（実測エディタ / 実測印刷 / 推定） |
| D3 | 計測が2系統。印刷側はズーム正規化なし・キャッシュなし |
| D4 | 印刷側がブロック座標を実測せず、自前のページ割り結果から逆算していた。**アンカー図形のズレの直接原因** |
| D5 | 箱の分割位置。編集側は実測行ボックス＋罫線スナップ、印刷側は子ブロック下端＋padding固定値 |
| D6 | 高すぎるブロックの分割。印刷側だけピクセルスライス |
| D7 | 印刷側が `layoutSection.columnGapMm` を無視 |
| D8 | 枠のchrome paddingがpx版とmm版で二重定義 |
| D9 | 問題番号フォントサイズを印刷側だけ独自コピー |
| D10 | `isProblemFrameArea` の重複定義 |
| D11 | 図形の幾何が二重実装。三角形の頂点clampが1px違う |
| D12 | 図形リッチテキスト・表のシリアライザが React版 / HTML文字列版で二重 |
| D13 | 図形によるページ増加のイプシロンが印刷側だけ12px |
| D14 | 本文DOMが `.sigma-doc-*` と `.print-*` の2系統 |

これらを個別に直しても、次の機能追加で新しい乖離が生まれます。**計算箇所を1つにする以外に恒久解はありません。**

## 新方針

```text
SigmaDoc
  └─ プロファイル投影 (getPrintableDocument)
       └─ ページキャンバス（唯一のレイアウトエンジン）
            └─ OutputSession（確定したDOMとrevision）
                 ├─ 画面: ページ窓としてプレビュー
                 └─ PDF : 同じページ窓を1ページずつ出力して結合
```

PDF生成の手順:

1. 表示中のPDFプレビューで、プロファイル投影済みドキュメントをページキャンバスに `presentation="paged"` で描画する
2. レイアウト確定を待つ（フォント・数式・画像・ページ割り）
3. 確定した `.page-canvas` をページ帯ごとに切った用紙窓と、`surfaceId` / `revision` / ページ数 / 用紙サイズをOutputSessionとして扱う
4. PDF保存を押したWebContents内で、同じrevisionの用紙窓を1ページだけ一時出力ルートへ複製する
5. `printToPDF` に用紙設定由来の `pageSize` を渡し、出力が1ページかつ同じMediaBoxであることを検証する
6. 全ページを順番にPDFへコピーし、結合後のページ数と全MediaBoxを再検証してから保存する

Chromiumには**複数ページの分割をさせません**。1回の`printToPDF`へ渡す内容は、すでに確定した用紙窓1枚だけです。Chromiumは文字・数式・SVGをベクターPDFへ描く役割に限定し、ページの境界や総数を決めません。

## 不変条件

守れなくなったらPDFがズレます。テストで固定してあります。

1. **レイアウト計算はドキュメント1つにつき1回だけ。** PDF側で再計測・再ページ割りをしてはいけません。印刷専用のページネーション関数を作らないこと。
2. **PDFに出るDOMは、表示中のプレビュー用紙窓のクローンであること。** PDF専用のブロックコンポーネント・CSSクラスを作らないこと。別ウィンドウでSigmaDocを再読込・再マウントしないこと。
3. **ブロック座標を算術で逆算しないこと。** 図形のアンカー解決は実測済みの矩形だけを使います（旧 `getMeasuredPrintBlockRects` が禁止事項の実例）。
4. **図形は画面と同じReactコンポーネントで描くこと。** SVG文字列シリアライザはPDFの経路に入れません。線をどこで止め矢印ヘッドをどこに置くかは `features/rendering/core/arrowhead-spec.ts`（頭の寸法と基準点）と `features/drawing/arrowhead-trim.ts`（図形ごとの短縮量）が唯一の出典で、Reactレンダラ・SVG文字列シリアライザ・ツールバーのプレビューはいずれもここを読みます。片方だけを直すと「画面では正しいがPDFでは違う」が戻ります。
5. **レイアウトはズーム非依存であること。** ズームは `transform: scale()` で見た目だけを変えます。CSSの `zoom` プロパティはスケール後の長さでレイアウトをやり直すため使用禁止です。
6. **用紙サイズはドキュメントの `pageLayout` が唯一の出典。** `printToPDF` にサイズをハードコードしないこと。
7. **PDFの入力は画面が表示しているのと同じドキュメント。** ディスク上の保存済みファイルを読み直さないこと。
8. **複数ページを1回の`printToPDF`へ渡さないこと。** 各呼び出しは必ず1ページを返し、結合後もページ数と用紙サイズを検証すること。
9. **確定しないレイアウトを出力しないこと。** タイムアウト時に暫定DOMを切り出さず、`stalled`としてfail-closedにすること。
10. **標準本文フォントをOSへ委ねないこと。** 標準ゴシックは同梱した`M PLUS 1p`、標準明朝は同梱した`Noto Serif JP`を編集面・プレビュー・PDFで共有し、丸数字・ローマ数字・数学記号などの不足グリフも同梱した`Noto Sans Symbols`と`STIX Two Math`で補うこと。旧SigmaDocが持つ`Yu Mincho`・`Hiragino Mincho ProN`・`MS PMincho`の標準明朝フォールバックは、描画時に`Noto Serif JP`へ解決する。利用者がOS固有フォントを明示的に選んだ箇所だけを例外とする。
11. **入力UIをレイアウトエンジンにしないこと。** 行内数式は編集中も`renderMathHtml`由来の静的DOMをレイアウト箱として残し、MathLiveはその上に絶対配置する。入力中のTeXも静的DOMへ同期し、行高・折返し・改ページは静的DOMだけで決める。MathLiveのShadow DOM、キャレット層、選択層の寸法を文書レイアウトへ混ぜないこと。これは`\kyoutsuuchoice`だけでなく、分数・前文マクロ・今後追加する数式コマンドにも適用する。

## OutputSession

OutputSessionはSigmaDocの正本ではなく、表示中のプレビューから導出した一時的な出力状態です。`PagedRenderSurface`が公開する`surfaceId`、`revision`、`pageCount`、`pageWidthMm`、`pageHeightMm`を一組として扱います。

PDF保存IPCは呼び出し元のWebContentsをそのまま使います。保存済みファイルを非表示ウィンドウで読み直しません。各ページの準備前と全ページの生成後にrevisionを照合し、途中でMutationObserverによる再カットが起きた場合は、異なるrevisionを混ぜずに書き出しを中止します。

1ページPDFは文字・数式・SVGをベクターのまま保持します。結合処理はページオブジェクトのコピーだけを担当し、SigmaDocのレイアウトや描画を再実装してはいけません。

### 5 について（ズーム）

以前は `.page-stack` に CSS の `zoom` を掛けていました。`zoom` は `transform` と違い**スケール後の長さでレイアウトをやり直す**ため、80%編集時に1段落あたり約0.5px、下に行くほど累積するズレが出ていました（15段落目で2.5px）。PDFは常に100%で切るので、100%以外で編集している間だけ画面の紙面が違う状態でした。

現在は `transform: scale()` です。`transform` は専有領域を持たないので、`.page-mode` が `--page-stack-natural-width/height`（スタックの非スケール `offsetWidth`/`offsetHeight`。ResizeObserverが公開）× ズーム倍率でスクロール領域を確保します。paddingの算術を二重に持つ必要はありません。

**スケールの読み取りは `getEffectiveZoom` に集約されています。** 祖先の `zoom` と `transform` の両方を掛け合わせます。素材サムネイルなど `zoom` を使う場所が残っているため、片方だけを見ると測定値がスケール倍そのままズレます。

非整数倍率（150%など）では、スケールされた矩形を割り戻すときにサイズの報告値に1px未満の端数が残ります。位置とページ割りは全倍率で厳密に一致します。

## PrintPreview の位置づけ

`components/print/PrintPreview.tsx` の静的レンダラは、**PDFの経路から外れました**。残る用途は次の3つだけです。

- `packages/viewer`（外部埋め込みビューア。Tiptapを公開バンドルに入れない制約があるため）
- ワークスペースのカードサムネイル
- テンプレートギャラリー

いずれも近似プレビューであり、**正確さが要求される出力ではありません**。ここに用紙出力を追加しないこと。静的レンダラとエディタの乖離はパリティテストで監視しますが、乖離してもPDFには影響しません。

## パリティテスト

`tests/e2e/pdf-parity.spec.ts` が、複数の実文書に対して次を検証します。

- 全ブロックの矩形が、エディタ画面とPDF出力面で一致すること（許容 0.5px ≒ 0.13mm）
- 全図形の矩形が一致すること
- 全行内数式（共通テスト選択肢と入れ子分数を含む）の矩形が一致すること
- ページ・段の割り当てが一致すること
- 枠が分割されて同じidが複数回出る場合は、出現ごとに突き合わせること
- ズーム倍率を変えても紙面が変わらないこと
- 実PDFのページ数がプレビューと一致すること

`electron/ipc/file.test.ts` は、表示中の同一OutputSessionから各ページを1回ずつ出力すること、revision変更時にfail-closedになること、結合後PDFのページ数が一致することを検証します。実PDFの画像比較は、用紙サイズ、最終ページ、フォント、数式、画像、overlayを含む回帰コーパスで別途行います。

対象: 複数ページの本文、2段組、手動改ページ、枠付き問題エリア、枠内の手動改ページ、ページを跨ぐ箱、ブロックにアンカーされた図形。

レイアウトに触る変更をしたら、このテストが唯一のゲートです。落ちたらPDFがズレています。

計測は**両側でレイアウトが収束してから**行う必要があります。フォント差し替えと図形アンカーの解決は数フレーム遅れて効くので、収束を待たない計測はレンダラのせいではないズレを報告します。同じ理由で、`PagedRenderSurface` はブロックと図形の位置を含むシグネチャが安定するまでページを切りません（キャンバスの高さだけを見ていたときは数px早く切っていました）。

## 遅れて走る装飾パスへの対応

ジオメトリが止まったあとに属性だけを書き換えるパスがあります。囲み枠(boxed run)の端の判定がそれで、計測パスが走るまでは全セグメントが「両隣に続きがある」状態のまま**安定して間違っています**。

```
100ms  state=pending  stage=[LR LR LR]   ← 未計測。全端connected
700ms  state=ready    stage=[-R LR L-]   ← 計測後。両端が閉じる
```

この間にクローンを取ると、枠が左右とも開いたPDFになります。**「安定するまで待つ」では直りません**（間違った値のまま安定しているため）。そこでステージにMutationObserverを張り、**変化したらページ窓を作り直します**。PDFは「確定したDOMのクローン」と定義しているので、DOMが変わればクローンも取り直すのが筋です。

作り直しのたびに `data-paged-surface-revision` が増えます。**出力を掴む側（PDF書き出しのready待ち、レイアウトテスト）は `state` だけでなくこのrevisionが止まるまで待ってください。** ページ数もサイズも変わらない作り直しがあるので、それらだけを見ていると差し替え前の面を掴みます。

## ページ割りパスの収束

**ページ収まりの判定には、前パスの「意図」ではなく、いま描かれているものを使ってください。**

単段フローは `topNat`（実測top − 適用済みgap）でページ収まりを決めます。この「適用済みgap」をレイアウト状態のマップから取っていた頃、DOMがまだ追いついていない瞬間に再計算が走ると、引き算の元と引く量が食い違いました。`topNat` がgap非依存でなくなるため、**同じドキュメントに自己整合的なレイアウトが複数生まれ、2つのマウントが別の答えに落ち着きます**（2pxズレる、または手動改ページが「もうページ先頭だから」と飛ばされて1ページになる）。並列実行時に3回に1回ほど再現していました。

`measureAppliedGapPx` が、実際に描かれている量をDOMから読みます。ブロックはProseMirrorのスペーサーwidget、エリアはフローユニットのmargin。どちらも「引き算の元になった計測」と食い違いようがないので、パスがいつ走っても収束します。

局所的な回避を2つ試して、どちらも症状を別の場所へ移しただけでした（「このページに既に置いたか」をパス内カウンタで判定 / 保存する矩形をパスが決めた位置に補正）。**判定材料を実描画に一本化するのが正解**です。

パリティテストはこの収束性も担保します。両側が同じエンジンで動く以上、ページや位置が食い違えば「同じドキュメントが2通りに落ち着いた」ということだからです。

この過程で潰した他のバグ:

- `.page-mode` の `min-width` にスタックの実測幅を戻すループ。スタックは `.page-mode` の100%幅なので際限なく太る。公開するのは高さだけにした（スタックは絶対配置で `.page-mode` の高さに触れないため安全）
- webフォント確定後の再計測。フォントは初回レイアウトの後に効き、flowの寸法が変わらないとResizeObserverが取りこぼす

## 囲み枠は「実際の矩形に1つ描く」

**囲み枠を、セグメントごとのborderで描かないでください。** run全体の矩形を実測し、そこに矩形を1つ描きます。

セグメントごとにborderを描いて端を揃える方式は、原理的に端数が残ります:

- **paddingは箱を大きくすることしかできません。** runの高さを決めているセグメント（背の高い `\sum` など）はpaddingが0になり、動かす手段がありません
- **隣にpaddingを入れると行ボックスが変わり、そのセグメントの相対位置が動きます。** 計測はpaddingを外した状態で行うので、この二次効果が見えません

実測で0.31pxずれ、`\frac` の隣で枠の下からborderの黒い帯がはみ出していました。0.3pxでもデバイスピクセルを跨げば1px見えます。

いまは `readRenderedRunFrames` がレンダリング後のrunの矩形を読み、`.boxed-run-frame` を絶対配置で1つ描きます。セグメントはborder boxを保ったまま（場所の確保と計測のため）**何も塗りません**。

- 端が1組しか無いので、食い違いようがありません
- **フィードバックしません。** 枠はフローの外に置かれるので、計測元のテキストを動かせません
- 折り返したrunは行ごとに矩形が分かれます（`getClientRects` の各行ボックスを使う）
- 位置決めの基準にするため、枠を持つ段落には `boxed-run-framed` を付けます

## 印刷側にしか無かったルールの移設

印刷側に「エディタが実装していないルール」が入っていたため、レンダラを一本化するとそのルールが失われます。**第2のrendererに戻すのではなく、唯一のレイアウトエンジン側へ移す**のが正しい直し方です。

### 解答エリアの確保分をページ収まり判定に入れる（移設済み）

`areaLayout.*.minHeightMm` が確保する空白はどのブロックの高さでもないため、単段フローの歩きに現れませんでした。枠付き問題は段落単位で置かれ、各段落は収まるので誰も送られず、確保した解答欄だけが用紙下端を突き抜けていました。

枠付き問題(内部に手動改ページが無いもの)を単段フローで1つの原子として扱い、高さはレンダリング済みエリアの実測から取ります。確保した空白は実測に含まれるので、別の計算を持つ必要はありません。

実装上の注意:

- 高さは**各エリアの高さの合計**。`bottom - top` にするとエリア間のgapを取り込み、自分が生んだ値を自分の判定に食わせることになります（2つのマウントが別ページに落ち着きました）
- gapのキーは `problem.id`。先頭エリアに適用される既存の規約に乗っています
- **ページに収まる問題だけを対象にします。** 収まらないものを原子扱いすると、ページカーソルが開始シートに残り後続が1ページ早くなります。用紙より背の高い枠付き問題を正しく扱うには、枠ごとページを跨いで断片化する必要があります（`tests/e2e/print-problem-pagination.spec.ts` に `test.fail()` で固定）

### 箱の分割数（誤検知だった）

180段落のcornerboxは、旧print rendererと同じく3つの断片になります。エディタでは**最初の断片が「その場でクリップされた元の箱」**で、続きだけが `.editor-box-fragment-viewport` になるため、viewportだけを数えると1つ少なく見えていました。分割ロジックに問題はありません。

## 全ページのクローンについて

各ページ窓は確定した紙面の**完全なコピー**を持ち、ページ帯の外はクリップで隠しているだけです。したがって:

- `data-sigma-doc-id` / `data-overlay-shape-id` / `data-flow-unit-id` は、その要素が実際に載るページの窓にだけ残します(`measurePageOwnership`)。おかげで `[data-sigma-doc-id="x"]` は1つだけ一致します。
- **それ以外のセレクタはページ数ぶん重複します。** 内容を数えたい場合は、窓を横断せずステージ(`.paged-surface-stage`)を見てください。

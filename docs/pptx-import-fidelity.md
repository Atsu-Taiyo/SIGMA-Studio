# pptx インポートの忠実度計測

「レイアウトが崩れていないこと」を人の目視ではなく機械で確かめるための取り決め。
比較コアは `apps/desktop/src/lib/powerpoint-fidelity.ts`、実教材での実行は
`apps/desktop/src/lib/powerpoint-fidelity.decks.test.ts`。

## 使い方

```bash
# 既定: 教材が無いので skip される（合成 fixture の単体テストだけが走る）
npm --prefix apps/desktop run test -- src/lib/powerpoint-fidelity.test.ts

# 実教材で計測する
SIGMA_PPTX_FIDELITY_DIR=/path/to/decks \
  npm --prefix apps/desktop run test -- src/lib/powerpoint-fidelity.decks.test.ts
```

- `SIGMA_PPTX_FIDELITY_DIR` **未設定**なら `apps/desktop/pptx-fidelity-decks/` を見る。
  そこにも `.pptx` が無ければ計測スイートは **skip**（CI・他の開発者を赤くしない）。
- `SIGMA_PPTX_FIDELITY_DIR` を**設定したのにディレクトリが無い / `.pptx` が 1 つも無い**場合は
  **失敗させる**。打ち間違えたパスで「何も測っていないのに緑」になるのが、この仕組みが
  防ごうとしている当の失敗モードだから（`apps/desktop/scripts/perf-probe.mjs` の
  フィクスチャ名チェックと同じ理由）。
- 実教材は**リポジトリに置かない**（著作権・サイズ・機密）。`apps/desktop/.gitignore` の
  `/pptx-fidelity-decks/` はそのための行。
- 計測結果もリポジトリに置かない。標準出力に出るレポートをそのまま読む。

## 何を測っているか

入力は「PPTX のバイト列」と「インポート済み `SigmaDocument`」。4 つの軸で突き合わせる。

| 軸 | 見るもの |
| --- | --- |
| `document` | スライド枚数、ページサイズ |
| `coverage` | 原本の描画オブジェクトがインポート結果に存在するか |
| `geometry` | 位置・サイズの px 差分、ページ外へのはみ出し |
| `text` | 本文の保全とフォントサイズ (pt) |

スライド枚数は**インポート結果が実際に到達したページ数**を図形の外接から測る
（`PageCanvasEditor` がシート数を伸ばすのと同じ考え方）。`metadata.source.slideCount` は
**使わない** — インポータがそこへ書くのは `slidePaths.length`、すなわち本ハーネスが
原本側の枚数を導くのと同じ値であり、突き合わせても値を自分自身と比べるだけで
`slideCountMismatch` が永久に発火しなくなる。まさにこのハーネスが防ごうとしている
循環そのものなので、インポート側は**測る**（訊かない）。インポータの申告値は
`declared` として並記するだけに留める。

結合キーは `overlaySnapshot.extensions["sigma.powerpoint"].shapeNames`
（`shapeId → cNvPr/@name`）。ページは図形の `y` を**ドキュメントから読み戻した**
ページ送り（`getPageMetrics(...).page.heightPx + PAGE_GAP_PX`）で割って求める。
EMU から計算し直すとページ境界付近で取り違えるため、ここは必ず出力側から読む。

### 重大度

- **重大 (error)**: `missingObject` / `pageSizeMismatch` / `textMissing` / `offPage` /
  幾何差分が 4px 超 / `slideCountMismatch`（下記の例外に当たらない場合）
- **警告 (warning)**: 幾何差分が 1px 超 4px 以下 / `textMismatch` / フォントサイズ 0.5pt 超のずれ
- **参考 (info)**: `groupDissolved` / `emptyPlaceholderDropped` / `unknownImportedShape` /
  `slideCountMismatch`（超過分がスライド外コンテンツで説明できる場合）

**スライド外（ペーストボード）のコンテンツは仕様どおり**なので error にしない。
スライド外に置かれた図形をそのまま取り込む結果ページ数がスライド数を超えることがあるが、
これは製品としての決定であって不具合ではない。**超過分が「実在するスライドに属する図形の
はみ出し」で説明できるときだけ** info へ落とす。条件は次の 2 つを両方満たすこと:

1. **全ての図形が自分の所属スライドを ID に記録している**（`ppt_shape_<slide+1>_…` として
   解釈できる）。解釈できない ID を「主張なし」として黙認すると、迷子の図形が自分自身を
   言い訳にでき、極端には全 ID が非対応の文書でこの軸が二度と発火しなくなる。
2. その記録スライドが**すべてスライド数の範囲内**であること。

存在しないスライドを主張する図形がある場合やページが減っている場合は、
本物のページ割り不具合なので error のままにする。

なお**ページ数が正しくても中身が迷子になる**ことはある。原本ではスライド内に収まっている
図形が自分のページ帯から外へ出た場合は `offPage` として error で報告する。これは
厳密幾何比較の対象外（回転あり等）のオブジェクトにも適用する——「別のページへ飛んでいる」の
判定に幾何の予測は要らないため。ただし原本の箱がスライド座標で分かる**直下オブジェクトに限る**。
グループの子は箱がグループ相対、グループ自身は箱が子から再計算されるので判定できない
（＝グループの子が誤ったページに落ちる事象は現状拾えない。既知の限界）。

**フォントサイズ軸は「グループが実際に拡大縮小している子」だけ対象外にする。**
グループは `a:ext / a:chExt` の比率で子のフォントサイズも拡大縮小するため、その場合の
描画サイズは予測できない——幾何軸が同じ連鎖の再実装を拒むのと同じ理由で `groupChild` として
記録する（黙って捨てはしない）。逆に `chExt === ext`（PowerPoint が普通のグループに書く値）
なら拡大縮小は起きず、サイズは原本どおりなので**通常どおり比較する**。
グループの子を一律に除外すると、px/pt 取り違えのような不具合がグループの中でだけ
無言になる——それはこのハーネスが唯一見つけた本物の不具合と同じ種類である。

**表（`p:graphicFrame` + `a:tbl`）の期待サイズは frame の `a:ext` ではなくグリッドから取る。**
Google Slides の書き出しは frame の `a:ext` にプレースホルダを書く（検証デッキの 2 例はいずれも
ちょうど 3000000×3000000 EMU）。実際の描画サイズは表自身のグリッド（`a:gridCol/@w` と
`a:tr/@h` の合計）で決まる。これは Google 自身のスライド描画と突き合わせて確認した——
deck04 スライド 5 の 3 列 9 行の表は約 216×444px で、315px 角ではない。

したがって期待サイズはグリッドから**ハーネス自身のパーサで**算出し、

- **位置と幅は厳密比較**（列はテキストで伸びないので幅は確定値）
- **高さは下限比較**（`a:tr/@h` は最小値で、行はテキストに合わせて伸びうる。
  宣言より高いのは正当、低いのは内容の切り落とし）

とする。**「比較しない」ではなく「グリッドと比較する」**である点が重要で、
比較をやめてしまうとインポータが intrinsic size の適用をやめてプレースホルダに戻っても
ハーネスは緑のままになる——それは「インポータがインポータに一致することを確かめる」検査に
戻ることを意味する。高さが下限比較であることは `intrinsicTableSize` として記録する。

1px という下限は恣意的な値ではない。`pptx-viewer-core` は座標を整数 px に
`Math.round` するので、それ未満を有意差として扱うことは原理的にできない。
4px の error しきい値は**暫定値**で、実教材の分布が出た時点で根拠付きで引き直す。

## なぜ独立したパーサを持つのか

期待値をインポータ自身の OOXML ヘルパから作ると、「インポータがインポータに
一致すること」を確かめるだけの循環した検査になる。そのため比較コアは
`fast-xml-parser` を **`preserveOrder: true`** で別に持つ。この設定は
ドキュメント順とグループの入れ子をそのまま保つので、インポータ側の
「タグでまとめる parse + 正規表現による `spTree` 切り出し」とは独立に読める。

共有しているのは次の 3 つだけで、いずれも OOXML/CSS の規約か、
出力側から読み戻した値であって、再導出ではない。

1. `EMU_PER_INCH = 914400`・96dpi — OOXML/CSS の定数
2. スライド順は `p:sldIdLst` + `ppt/_rels/presentation.xml.rels` — OOXML の規則。
   独自に実装しているので、食い違えばそれ自体が検出結果になる
3. ページ送りは**インポータの決定**なので、ドキュメントから読み戻す

`pptx-svg` は幾何の正解として使わない（node に `SVGSVGElement` が無く、
そもそも「仕様」ではなく別のレンダラの意見であるため）。目視三点比較には有用なので、
実教材の調査工程で使う。

## 「厳密比較の対象外」を必ず報告する理由

素朴に期待値を計算すると **false positive を量産する**。グループの子は
`a:chOff`/`a:chExt` の連鎖でスケールされ、グループ自身の箱は子から再計算され、
プレースホルダはレイアウト/マスターから幾何を継承する。これらを再実装すれば、
実装が正しくても差分が出る。

そこで**厳密な幾何比較は次を全て満たすものだけ**に限る。

- `p:spTree` の直下（グループ配下でない）
- `p:grpSp` そのものでない
- 自前の `a:xfrm`（`a:off` と `a:ext` の両方）を持つ
- `a:xfrm/@rot` が無いか 0

`@flipH`/`@flipV` は**対象に含める**。鏡映しても軸平行の外接矩形は変わらない。

上記を外れたものは**握り潰さず** `notStrictlyCompared` に理由付きで積む
（`group` / `groupChild` / `rotated` / `inheritedGeometry` /
`inheritedFontSize` / `nonTextShapeKind` / `ambiguousName` /
`unmappedGraphicFrame` / `intrinsicTableSize`）。そして

```
counts.strictlyCompared + counts.notStrictlyCompared === counts.sourceObjects
```

を不変条件として単体テストで固定している。これが「黙って skip した分だけ
数字が良く見える」ことを防ぐ唯一の歯止め。

**被覆率とテキストは対象外のオブジェクトにも適用する。** グループの子が消えたなら、
その幾何が予測しづらいかどうかに関係なく、それは失われた内容である。

唯一の例外が**フォントサイズ**で、これは text 軸に属しながら「サイズが予測できるか」に
依存する。拡大縮小するグループの中でだけは比較せず `groupChild` として記録する
（上記「重大度」節）。本文そのものの保全は、この例外に関係なく常に比較する。

## このハーネスが分かること・分からないこと

**「数字が動かなかった」ことは正しさの証拠にならない。** 実教材でその経路に到達しないだけかもしれない。

実例: グループのテキスト計上を直した際（WI-6）、`isDrawable` が「テキストが空の
プレースホルダは対象外」という判定だったため、**`p:ph` を持つグループが計測対象から
丸ごと脱落する退行**を同時に入れてしまった。ところが検証用の 8 デッキには
プレースホルダなグループが 1 つも無いため、**退行の前後でデッキの数字は完全に同一**だった。
これを捕まえたのはレビューの合成プローブだけである。

したがって:

- **実データ計測**は「現実に何が起きるか」を教えるが、データが踏まない経路については何も言わない
- **合成 fixture / プローブ**は経路を狙って踏めるが、現実の分布は教えてくれない
- **どちらも他方の代わりにならない。** 分類規則を変えたら、実教材の数字が動かなくても
  合成 fixture で両方向（過小報告・過剰報告）を確かめること

## これまでに何を見つけたか（正直な実績）

実教材で報告された error 4 種のうち、**3 種はハーネス自身の欠陥**だった。

| 報告された種別 | 実体 | 直した場所 |
| --- | --- | --- |
| `fontSizeDelta` ×355 | **本物のインポータ不具合**。`pptx-viewer-core` が run のフォントサイズを px で返すのを pt として扱っており、プライマリ経路の全テキストが 4/3 倍だった | インポータ |
| `missingObject` ×30 | ハーネスの欠陥。図形→ページ帰属を `floor(y / stride)` で推測しており、スライド外コンテンツとグループの子を取り違えていた | ハーネス |
| `textMissing` ×18 | ハーネスの欠陥。`p:grpSp` に子のテキストを計上していた（グループは `p:txBody` を持てない） | ハーネス |
| `slideCountMismatch` | ハーネスの欠陥。インポータの申告値と原本枚数という**同じ値どうし**を比較していて発火しえなかった | ハーネス |

この比率は驚くようなことではない。**新しい計測器は、最初のうち自分自身を測っている**。
新しい軸を足したら、測られる側を直す前に「この告発は本当か」を実データで 1 回監査すること。
それでも `fontSizeDelta` 1 件だけで、緑のテスト 25 本をすり抜けていた 33% の文字サイズ誤差が
見つかったのだから、この作業には十分な価値がある。

## 比較コア自体のテスト

実教材が無い環境でも「ハーネスが壊れた」と分かるように、比較ロジックは
合成 fixture の単体テスト（`powerpoint-fidelity.test.ts`）で守られている。
`readPptxSourceOutline` 用の fixture は手書きの OOXML を JSZip で固めたもので、
`powerpoint-import.test.ts` の fixture と同じ流儀に揃えてある。

新しい乖離を潰すときは、**まず最小の合成 pptx で赤くしてから**インポータを直す。
実教材はコミットできないので、回帰テストは常に合成 fixture 側に残す。

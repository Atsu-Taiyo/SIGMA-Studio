# Design Rules

## Purpose

この文書は、Sigma Studio のUIと教材出力に共通するデザイン判断の基準を定義する。

基本方針は、とにかく直感的でシンプルなデザインにすること。ミニマルで洗練された印象を保ち、白、黒、グレーを基調にした静かな見た目にする。操作は説明文に頼らず、アイコン、配置、状態変化によってすぐに理解できることを優先する。

迷った時は、見た目の凝った表現よりも、ユーザーが迷わず操作できることを優先する。

## Core Principles

### 1. Intuitive And Simple

すべてのUIは、初見でも意味と操作がすぐに分かることを目指す。

- 画面上の要素数を増やしすぎない
- 操作の流れを短く、予測しやすくする
- 同じ操作は常に同じ位置、同じ見た目、同じ挙動にする
- 重要な操作ほど見つけやすく、補助的な操作ほど控えめにする
- 説明が必要になるUIは、配置、アイコン、ラベル、状態表示を見直す

### 2. Minimal And Refined

画面は、編集作業と教材内容が主役になるように設計する。

- 装飾は最小限にする
- 強い色、過度な影、派手なグラデーションは使わない
- 余白、線、タイポグラフィ、アイコンで階層を作る
- ユーザーが長時間作業しても疲れにくい静かな見た目にする

### 3. State Awareness

ユーザーが、現在のアプリの状態を常に理解できるようにする。

- 読み込み中、保存中、同期中、エラー、未保存、選択中を明確に示す
- 状態表示は作業の邪魔にならない位置と強さにする
- 重要な状態はアイコン、ラベル、色、動きのいずれかを組み合わせて伝える
- 長時間かかる処理では、処理中であることと操作可能範囲を明確にする
- 状態が変わった時は、画面内の該当箇所に近い場所で変化を見せる

読み込み中は、原則としてShimmerを利用する。単なるスピナーだけに頼らず、読み込み後に表示されるUIの形を保ったプレースホルダーを見せる。

### 4. Monochrome And Gray First

基本色は白、黒、グレーで構成する。グレーは単なる補助色ではなく、面、境界、階層、状態、非アクティブ要素を表現するために積極的に使う。

```text
background     #FFFFFF
surface        #FAFAFA
surface-soft   #F7F7F7
surface-muted  #F1F1F1
surface-strong #E9E9E9
border-subtle  #E5E5E5
border         #DADADA
border-strong  #BDBDBD
text-primary   #111111
text-secondary #555555
text-muted     #8A8A8A
text-disabled  #B0B0B0
```

グレーの使い分け:

- 背景差: パネル、ツールバー、インスペクタ、空状態
- 境界線: セクション、カード、ブロック、入力欄
- 状態: hover、selected、disabled、loading
- 階層: メタ情報、補助ラベル、非アクティブな操作
- Shimmer: 読み込み中の骨格表示

アクセントカラーは、状態や警告など意味がある場面に限定する。

- 選択中、フォーカス中、編集中の状態
- エラー、警告、成功、保存状態
- 数式、図、画像などの種類を識別する必要がある場合

アクセントカラーを使う場合も、画面全体の印象が白、黒、グレー基調から外れない濃度と面積に抑える。

### 5. Icon-Led Interaction

主要な操作は、可能な限りアイコンを中心に表現する。

- 保存、戻る、進む、削除、複製、拡大、縮小、整列などはアイコンボタンを使う
- 太字、斜体、数式、画像、図形、表などもアイコンで表す
- アイコンだけで意味が曖昧な操作にはツールチップを付ける
- 重要な破壊的操作は、アイコンだけで即実行せず確認または取り消し可能にする

説明文は常時表示しない。必要な補助情報はツールチップ、プレースホルダー、空状態、または一時的なガイドとして表示する。

### 6. Progressive Disclosure

画面にすべての情報や操作を常時表示せず、ユーザーの関心に応じて必要なものを段階的に開示する。

- 補助情報、詳細、追加操作は、ホバー時に表示する段階的開示を積極的に使う
- 初期状態はコンパクトに保ち、ホバーで情報を開示しても周囲のレイアウトを不安定にしない
- 主要操作や重要な状態は、ホバーしなければ存在が分からない設計にしない

### 7. Calm And Polished Product UI

静かで洗練されたプロダクトUIを目指す。要素を装飾で目立たせるのではなく、余白、整列、薄い面の差、短いラベルによって完成度を高める。

- 1画面の主役を1つに絞り、主要な入力、会話、教材、または選択中の対象へ自然に視線が集まる構成にする
- 初期画面、空状態、AIとの会話、モーダルなど、作業対象が限定された画面は中央寄せの適切な最大幅を設け、周囲に十分な余白を取る
- 背景は白からごく薄いニュートラルグレーを使い、面の階層は強い影ではなく、薄い背景差と1pxの境界線で表現する
- 影は浮いていることを伝える必要があるモーダル、ポップオーバー、フローティング操作に限定し、広く柔らかく、ほとんど意識されない強さにする
- 角丸は共通スケールに揃える。文字を含む小さなボタンや入力欄は8-12px、大きなパネルや入力面は16-24pxを目安にする。完全なピル形状は選択状態、チップ、短いステータスに限定し、幅と高さが同じアイコンボタンは真円を標準とする
- 選択中のナビゲーションやタブは、濃い枠線ではなく薄いグレーの面で包み、未選択項目との違いを静かに示す
- アイコンは線の太さと大きさを揃え、ラベルの左に置く場合は文字のベースラインと視覚的な中心を合わせる
- 見出しは過度に太くせず、本文、補助情報、メタ情報を文字サイズ、ウェイト、グレーの濃度で段階づける
- バッジ、サービスアイコン、エラー、削除、主要アクション以外ではアクセントカラーを広い面積に使わない
- 同じ種類のカード、ナビゲーション項目、アクションは、余白、アイコン位置、文字位置、境界線、角丸を揃え、反復による整然さを作る

## Spacing System

余白、パディング、要素間隔は感覚で決めず、固定のスペーシングスケールと共通レイアウトコンポーネントで管理する。新規UIと、既存UIを改修する範囲ではこのルールを必須とし、既存箇所は触れた単位で段階的に移行する。

### Spacing Scale

レイアウトに使用できる値は次に限定する。値の定義はCSSカスタムプロパティを唯一の基準とし、コンポーネント側はトークン名だけを受け取る。

| Token | Value | 主な用途 |
| --- | ---: | --- |
| `none` | `0px` | 余白なし |
| `xs` | `4px` | 密接したアイコン、最小の操作間隔 |
| `sm` | `8px` | アイコンとラベル、標準の小要素間隔 |
| `md` | `12px` | フォーム内、コンパクトな行 |
| `lg` | `16px` | カード、パネル、標準の内側余白 |
| `xl` | `24px` | セクション、モーダル、主要な入力面 |
| `2xl` | `32px` | 画面の外側余白、主要領域間 |
| `3xl` | `48px` | 空状態、集中画面の大きな余白 |
| `4xl` | `64px` | 特別に広い導入画面の余白 |

- `margin`、`padding`、`gap`、`row-gap`、`column-gap`には、原則として上記以外の数値を直接指定しない
- `1px`は境界線、`2px`はアイコンや文字の光学補正に限って使用でき、通常のレイアウト間隔には使わない
- 子要素の個別`margin`で間隔を作らず、親レイアウトの`gap`で管理する
- レスポンシブに余白を変える場合も、任意の中間値を作らず、ブレークポイントでトークンを切り替える
- 負の余白は原則禁止する。キャンバスの座標処理、ヒット領域、印刷配置などで必要な場合は、理由をコードコメントに残す
- オーバーレイ座標、図形サイズ、印刷寸法、ユーザーが直接指定する値は、このUIスペーシングスケールの対象外とする

標準レシピ:

| Context | 値 |
| --- | --- |
| 隣接するアイコンボタン | `4px` |
| アイコンとラベル | `8px` |
| 標準の要素間隔 | `8px` |
| フォーム項目間 | `12px` |
| ボタン・入力欄の内側 | 上下 `8px` / 左右 `12px` |
| コンパクトなリスト行 | 上下 `8px` / 左右 `12px` |
| カード・パネルの内側 | `16px` |
| モーダル・主要入力面の内側 | `24px` |
| セクション間 | `24px` |
| 主要領域間 | `32px` |
| 画面の左右余白 | 通常 `32px` / 狭い画面 `16px` |
| 空状態・集中画面の大きな余白 | `48px` |

### Layout Components

共通レイアウトコンポーネントは `apps/desktop/src/components/ui/layout/` に集約し、次のプリミティブを標準とする。

- `Stack`: 縦方向の配置と`gap`を管理する
- `Inline`: 横方向の配置、`gap`、折り返し、垂直位置を管理する
- `Inset`: カード、パネル、入力面などの内側`padding`を管理する
- `Center`: 最大幅、左右中央寄せ、画面端のガターを管理する
- `Grid`: 同種カードや繰り返し要素の列数と`gap`を管理する

これらのコンポーネントは、スペーシングトークン名を型付きのpropsとして受け取り、任意のpx値は受け取らない。新規・改修UIでは、単純な縦横配置や内側余白のために個別の`div`と生の`margin`、`padding`、`gap`を増やさない。

- コンポーネント固有の見た目は各コンポーネントが持ち、兄弟要素との間隔は`Stack`、`Inline`、`Grid`が持つ
- カードやモーダルの内側余白は`Inset`を使い、外側余白と混在させない
- レイアウトプリミティブは配置だけを担当し、色、境界線、影、業務ロジックを持たない
- 既存UIの改修では、変更対象のまとまりだけをプリミティブへ移行し、無関係な画面まで一括で書き換えない
- 例外的に生の値が必要な場合は、既存値の流用だけで済ませず、スケールで表現できない理由をコードコメントに残す

### Shared Surface Tokens

角丸、集中領域の最大幅、フローティング面の影、モーダルの積層もCSSカスタムプロパティを基準にする。

| Token | 意図 |
| --- | --- |
| `--radius-control` | ボタン、入力欄、小さな操作面 |
| `--radius-round` | 幅と高さが同じアイコンボタンを真円にする共通値 |
| `--radius-panel` | カード、ポップオーバー、フローティングウィジェット |
| `--radius-dialog` | モーダルなど大きな集中面 |
| `--content-width-sm` / `md` / `lg` / `xl` | `Center` とモーダルの最大幅 |
| `--shadow-floating` | 浮いている必要がある面だけに使う共通の弱い影 |
| `--z-modal` / `--z-modal-nested` / `--z-tooltip` | 通常モーダル、入れ子モーダル、Tooltipの積層順 |

共通UIの意図と責務境界は `apps/desktop/src/components/ui/README.md` を正とする。新しい共通コンポーネントを追加する場合は、公開exportのJSDocと同READMEの一覧を同時に更新する。

## Layout

### Workspace

編集画面は、教材本文を中心に置く。

```text
top toolbar
left navigation / document outline
center editor canvas
optional right AI sidebar
bottom status or export feedback
```

教材要素の詳細設定を常設サイドバーへ出さない。問題、box、コードブロックなどコンポーネント単位の設定は、対象のHover時に右上へ出る3点ボタンから設定ダイアログを開く。コードの言語やブロック単体の背景もこの設定に置き、全体ツールバーへ常設しない。中央の編集領域を最も強く、補助パネルは薄い背景、細い境界線、小さな文字で控えめに見せる。

### Editor Chrome Layouts

編集画面のクローム（メニューバーとコマンド面）は2系統ある。どちらを使うかはユーザーが選ぶ設定で、初回起動時に1画面で選ばせる。

- 既定は**Googleドキュメント風**（1段のツールバー）。迷ったらこちらに寄せる。
- もう一方は**Word風**（タブで切り替えるリボン）。Wordのブランドカラー（青）は使わず、面と線は無彩色パレットに収める。選択中・フォーカス中・押下中などの**状態表現に既存のアクセントを使うのは従来どおり可**。
- 選択中のタブは濃い枠線で囲まず、**薄いグレーの面**で示す（`### 4. Monochrome And Gray First` のグレーの使い分けに従う）。
- リボンのグループ見出しは 11px / `--text-muted`。コマンドそのものより弱く置く。グループ間の区切りは影ではなく 1px の縦罫。
- クロームの高さは `--editor-chrome-height` と `--editor-statusbar-height` のトークンで管理する。本文キャンバスの `calc(100vh - …)` に生のpxを書かず、両方を引く（レイアウトごとに行数が違うため、数値を散らすと必ず片方だけずれる）。docsでは `--editor-statusbar-height` は `0px` なので、同じ式のままdocsの見た目は変わらない。
- コンテキストタブ（図形の書式など）は**対象を選択したときだけ**出す。ツールを構えただけでは出さない（中身が全部disabledのタブへ飛ばされる）。選択を解除したら、直前にユーザーが自分で選んだタブへ戻す。
- 本文ブロックのうち箇条書きと番号付きリストはツールバーへ直接置き、引用、コードブロック、区切り線、囲み枠は「その他のブロック」メニューへまとめる。

Word風は Word 365 の画面構成に倣う。色と余白は上記の無彩色パレット・`--space-*` のまま。

- **ファイルタブは Backstage**（編集画面を覆う1画面）にする。左に縦のナビ（← 戻る / ホーム / 新規 / 開く / 情報 / エクスポート / オプション / ヘルプ）、右に選択中セクションの内容。**Backstageのコマンドには必ず文字ラベルを付ける**（アイコンのみに落とすと動線が読めなくなる。これがWord風初版の実際の失敗）。Esc / ← / ファイルタブ再クリック / 他のタブのクリックで閉じ、**コマンドを押したら必ず閉じる**（本アプリのダイアログは背面を `inert` で隔離するので、開いたままだと閉じた先に忘れられた全画面が残る）。
- **タイトル行は 左端アイコン → クイックアクセスツールバー（保存状態・元に戻す・やり直す）→ 中央に教材タイトル → 右端の常設アクション**。タイトルを「残りの領域の中央」ではなく**行の中央**に置く（左右の列を同じ幅にする）。undo/redoはホームタブに置かない（Word 365 2023+ と同じ）。
- **リボン本体は2段構成**。グループの左に大ボタン（アイコンの下にラベル）、右に小ボタンを2段に積む。ダイアログランチャー（↘）は**対応するダイアログが実在するグループにだけ**付ける（押しても何も起きないボタンを作らない）。同名の大ボタンと衝突しないよう、ランチャーのアクセシブル名は「…ダイアログを開く」にする。
- **リボンは折りたためる**。折りたたむとタブ行だけになり、タブを押すと本体が一時的に浮いて出る（本文は動かさない = 高さトークンを変えない）。閉じるのは 外側クリック / Esc / 同じタブの再クリック / 展開ボタン / タブのダブルクリック / Ctrl+F1。畳んだ状態は次回起動時も保つ。
- **ステータスバーは画面下端**に置き、左に「ページ N / M」、右にズーム。ズームは表示タブにも残す（Wordも両方に持つ）。読み上げが鳴り続けるので `role="status"` にはしない。
- 同じコマンドが複数の面に出ることは受容する（ワークスペース、コメント表示、ズームなど。Word自身がそう）。ただし**同時に可視にはしない**（Backstage表示中はタイトル行・タブ行・ステータスバーのコマンドを消す）。見えていない本文へコマンドが効く状態を作らないこと。
- **新しいコマンドを追加するときは、両レイアウトでの置き場所を決めてから実装する。** 片方だけに足すと、もう一方のレイアウトでは到達不能なコマンドになる。これは規約であると同時に**機械的に担保されている** — `tests/e2e/ui-layout-parity.spec.ts` が両レイアウトのコマンド集合を双方向で突き合わせ、片側にしか無いコマンドがあれば落ちる。意図的な差分は理由付きの許容リストに載せる（実体の無くなったエントリも検出される）。

### Workspace Home

- 同じワークスペース・フォルダ内で教材を新規作成・複製・改名するとき、同名なら「教材名 2」「教材名 3」と連番を付ける。編集画面の改名は確定時に保存し、一覧へ戻る前に保存中の処理と未保存変更を反映する。
- 新規の無題教材を何も編集せずタブの×で閉じたら、教材自体も一覧から除く。名前変更・入力・書式変更をした教材は残す。最後の空タブを閉じた場合はワークスペースへ戻る。

教材一覧画面（`/workspace`）は、Google Driveのようなファイルブラウザの構成にする。

```text
header: brand / centered pill search / local save status + account
left sidebar: 「新規」ボタン / ワークスペース一覧
content: 多階層パンくず / グリッド⇄リスト切替 / フォルダと教材の一覧
```

- グリッド（カード）とリストの2表示を切替でき、選んだ表示形式は保存して次回起動時も維持する
- リスト表示は「名前」「更新日時」「場所」の列を持つ表にする。列見出しクリックで並び替え、もう一度クリックで昇順・降順を反転する。並び順に関わらずフォルダは常に教材より上に表示する
- クリックは選択、ダブルクリックで開く（Google Driveと同じ挙動）。設定やメタ情報のパネルは常設しない
- 名前変更はダイアログを開かず、カード／行の名前をその場でインライン編集する
- パンくずは現在のフォルダまでの階層をすべて表示し、途中の階層をクリックすればそこへ戻れる
- フォルダはグリッドではカード、リストでは表の行で表現し、操作ボタンはホバー時のみ表示する
- ワークスペースの削除は確認ダイアログに含まれる教材・フォルダの件数を明示し、最後の1つは削除できない
- 保存・エラーなどの状態は左下の一時的なトーストで伝え、画面に常駐させない

### AI Agent Activity

サイドバーのAIエージェント実行表示は、Codex CLIのような1行のステータス表示を基本にする。

- 実行中は処理内容に対応するモノクロのThinking OrbとテキストShimmerで現在の処理を1行で示し、経過時間を添える。Orbは実行中の状態表示に限定し、完了後や静的な装飾には使わない
- 本文キャンバス上の実行アンカーと図形ロックOverlayは、処理状態のOrbではなく実行元を識別できる各AIプロバイダのロゴを使う
- 詳細ログ（推論・プラン・イベント）は折りたたみ、求められたときだけ展開する
- 枠線や背景色のついたチップにせず、テキスト中心の控えめな表現にする

### Density

教材編集ツールとして、過度に余白を広げすぎない。

- ツールバーはコンパクトにする
- アイコンボタンは一定サイズに揃える
- リスト、アウトライン、プロパティはスキャンしやすい密度にする
- 本文キャンバスには十分な余白を持たせ、教材の読みやすさを優先する
- 初期画面、空状態、モーダル、AIの入力開始画面は、編集画面の密度をそのまま持ち込まず、中央の主役を囲む余白を広く取る

### Cards

カード表現は、個別の教材ブロック、モーダル、一覧アイテムに限定する。

- ページ全体をカードの連続にしない
- カードの角丸は大きさに応じた共通スケールに揃え、画面ごとに異なる角丸を増やさない
- カード内にさらにカードを入れない
- 影よりも境界線と背景差で区切る

## Typography

本文、UI、数式の読みやすさを優先する。

- UIラベルは短くする
- 説明文を増やすより、配置とアイコンで意味を伝える
- 見出しは太さとサイズで階層を作り、装飾に頼らない
- 文字間隔は標準を基本にする
- 教材中の文字サイズは1ptから選択でき、1pt以上の数値（小数も含む）を直接入力できるようにする。選択範囲への適用と保存後のサイズを保つ
- 行の高さは、その行に含まれる文字サイズ・数式と段落の行間倍率から決める。小さい文字だけの行に標準本文サイズの最低高さを残さず、同じ段落でも折り返した各行に必要な高さを確保する。段落下余白・見出し前後の余白・フッター領域の高さは別に扱う
- 長いラベルは折り返し、ボタンやパネルからはみ出さないようにする

推奨階層:

```text
page title      24-28px / semibold
section title   18-20px / semibold
panel title     13-14px / semibold
body            15-16px / regular
ui label        12-14px / medium
meta            11-12px / regular
```

## Controls

共通コンポーネントを置いただけで、UIの仕上げを完了としない。新規UIと改修対象では、閉じた状態のボタン・入力欄から、開いたメニューまで一体として整える。

- ブラウザやOSの既定の見た目を残さず、背景、境界線、角丸、高さ、余白、文字、アイコンを既存の共通トークンに揃える
- 通常、ホバー、フォーカス、選択、無効の状態を実画面で確認する。見た目を変えても、入力の意味、アクセシブルな名前、キーボード操作を失わない

### Buttons

ボタンは操作の重要度で見た目を分ける。

- Primary: 主要操作に限定する
- Secondary: 通常操作
- Ghost/Icon: ツールバー、インスペクタ、ブロック操作
- Danger: 削除や破壊的操作
- 削除ボタン、削除アイコン、削除メニュー項目は、マウスをかざした時に赤色へ変化させ、破壊的な操作であることを明確にする
- アイコンだけのボタンは、AIチャットの上向き矢印の送信ボタンを基準に、幅と高さを揃えた真円を既定とする
- 文字を含むボタンは `--radius-control`、真円のアイコンボタンは `--radius-round` を使い、画面ごとに形状を上書きしない

ツールバーでは、テキストボタンよりアイコンボタンを優先する。テキストを使う場合は、ユーザーが迷いやすい主要コマンドだけにする。

box操作・コードブロック設定のように対象の3点ボタンから開く小さな操作メニューは、タイトルと閉じるボタンを置かず、外側のタップまたは `Escape` で閉じる。言語などの選択メニューを重ねている間は、最初の `Escape` で選択メニューだけを閉じる。

それ以外のダイアログやポップオーバーを閉じるだけの操作は、右上の `X` アイコンボタンで表現する。フッターや本文内に「閉じる」「キャンセル」だけのテキストボタンを重複して置かない。取り消しと保存のようにユーザーが明示的に選ぶ必要がある場合だけ、文脈に合うテキストボタンを置く。

### Inputs

入力欄は、何を入力する欄かを画面上で分かるようにする。

- `x:` / `y:` のような短い識別ラベルは、説明文ではなく入力値の意味を示すUIとして扱う
- 横並びの入力欄、座標、範囲、サイズ、余白など、順序だけでは意味を誤読しやすい項目には小さなラベルを付ける
- ラベルは入力欄の近くに置き、視線移動なしで値との対応が分かるようにする
- インスペクタやツールバーでは、密度を保ったまま誤読を防ぐ。広い余白や長い説明文で解決しない
- プレースホルダー、aria-label、ツールチップだけを、値の意味を示す唯一の手段にしない
- 数値欄のOS標準スピナーをそのまま見せない。増減操作が必要な場合は、直接入力と併用できる、アプリの見た目に揃えた `−` / `＋` ボタンを使う
- 角丸など連続的に見た目を調整する値には、数値欄と同期するスライダーを併用する。スライダーのトラックとつまみも共通の配色・状態表示に揃える
- 数値の単位、最小値、最大値、刻みを揃え、空欄や小数の入力途中を妨げない。確定時は範囲内の値に整え、上限・下限で増減ボタンを適切に無効にする

### Selects And Pickers

選択肢から値を選ぶUIは、すべてアプリ内で実装したメニューで表示する。OSが描画するドロップダウン、カラーパネル、日付ピッカーは、アプリのデザイン言語から外れるうえ、プラットフォームごとに見た目も操作も変わるため使わない。

- ネイティブの `<select>` は使わない。共通の `Select` (`apps/desktop/src/components/ui/Select.tsx`) を使う
- `Select` は、閉じている時は現在値と `ChevronDown` だけを見せ、開いた時にアンカー付きのポップオーバーで選択肢を出す。選択中の項目にはチェックを付ける
- 共通の `Select` を使っていても、呼び出し側の枠・背景・余白が欠けた標準ボタンのような見た目を残さない。線種や文字の太さなど、見本で違いが分かる選択肢にはメニュー内に見本を添える
- ダイアログ内で選択メニューが開いている間は、最初の `Esc` でメニューだけを閉じる。親ダイアログまで同時に閉じない
- キーボードだけで完結させる: `Enter` / `Space` / `↑` / `↓` で開き、`↑` `↓` で移動、`Home` / `End` で端、`Enter` で決定、`Esc` で取り消して呼び出し元へフォーカスを戻す
- `<input type="color">` は使わない。色は見本 + 色作成ダイアログ (Color を参照) から選ぶ
- `<input type="date">` `<input type="time">` など、OSのピッカーを開く入力型も同じ理由で避ける
- 例外はOSでなければ実現できないものだけ: ファイル選択 (`<input type="file">`、`dialog.showOpenDialog` / `dialog.showSaveDialog`) などのOSファイルピッカー

### Color

色は見本から選ぶことを基本にし、任意の色は「カスタム」段の `+` から開く色作成ダイアログで作る。

- 色作成ダイアログは、彩度×明度の面、色相スライダー、HEXとR/G/Bの数値欄を持つ。不透明度を編集する呼び出しでは、市松模様の上に色を敷いた不透明度スライダーとA欄を加える
- 彩度×明度の面と色相の虹は編集対象そのものなので色を持つ。枠、文字、ボタン、面は白黒グレー基調を守る
- 面のようなポインタ専用のコントロールには、必ず数値欄などのキーボードで完結する代替経路を用意する
- 編集結果をその場で観察する面は、背面を暗くするモーダルにしない
- 保存形は色 (`#rrggbb`) と不透明度 (0..1) を分けて持つ。8桁のHEXは入力と表示のための表記であって、保存形にしない
- 「塗りなし」と「不透明度0%の色」は別物として、内部状態でもUI表示でも区別する
- 実行環境にない機能 (スポイトなど) のボタンは、`disabled` で置かず描画しない

### States

すべての操作要素に状態を用意する。

- default
- hover
- active
- selected
- focused
- disabled
- loading
- error

状態差は、色だけに依存しない。背景、境界線、アイコン、ツールチップ、補助テキストを組み合わせる。

### Loading

読み込み中はShimmerを標準のローディング表現にする。

- エディタ本文、アウトライン、プロパティ、一覧、カードは実際のレイアウトに近いShimmerを表示する
- **待ち中の画面**（AI実行、検索、履歴読み込み、結果待ちなど、完了までユーザーが待つUI）でもShimmerを使う。AI実行ではThinking Orbを状態アイコンとして併用できる。Circular Loading（スピナー）だけに頼らない
- 実装は共通の `Shimmer` コンポーネント（`apps/desktop/src/components/ui/Shimmer.tsx`）と `.ui-shimmer-text` / `.ui-shimmer-surface` を優先する
- Shimmerはグレーの明度差、または透明度の緩やかな上下で表現し、控えめで上品な動きにする
- 読み込み後のレイアウトと大きく変わらないサイズで表示し、表示完了時のレイアウトシフトを抑える
- 小さなアイコンボタン単体の処理中は、ボタン内のloading状態または無効状態で示す
- 画面全体をブロックする読み込みは、初回表示やファイル切り替えなど必要な場面に限定する
- 保存中や同期中はShimmerではなく、ステータス表示で処理中であることを伝える

Shimmerの動きは遅めにし、強い点滅や派手なグラデーションにしない。

### Tooltips And Menus

ツールチップは短く、操作名を中心にする。

```text
良い例: 数式を挿入
悪い例: ここをクリックすると文書内に新しい数式を追加できます
```

- アイコンだけでは結果が曖昧な操作に限って使い、すべてのアイコンへ機械的に付けない
- 「選択範囲を太字に」「図形を選んで挿入」のように、操作後の結果を一行で示す
- 対応するショートカットがある場合は説明と分けて `kbd` で表示する
- ショートカットは既定値を直書きせず、ユーザー変更後の現在有効な割り当てを表示する
- 割り当てが解除されている場合は、古い既定キーを残さずキー表示を省略する

詳細な選択肢は、常時表示ではなくメニュー、ポップオーバー、インスペクタに収める。

### Dialogs

確認、入力、通知を含むすべてのダイアログは、アプリ内で実装されたダイアログコンポーネントで表示する。OSネイティブのダイアログはアプリのデザイン言語から外れるため、いかなる場面でも使わない。

- `window.alert` / `window.confirm` / `window.prompt` は禁止。ESLintの `no-alert` で機械的に防いでいる
- Electronメインプロセスの `dialog.showMessageBox` / `dialog.showErrorBox` も禁止。メインプロセス起点の確認や通知は `menu:action` などでレンダラーへ転送し、アプリ内UIで表示する
- `data:text/html` を読み込む即席の `BrowserWindow` をダイアログ代わりに作らない
- 実装は既存パターンに従う: backdrop + ダイアログ面 (`--radius-dialog`、`--z-modal`)、閉じる操作は右上の `X`、破壊的操作は `button danger`。参考実装は `WorkspaceCreateDialog` / `WorkspaceDeleteDialog` / `WorkspaceConfirmDialog`
- 例外はOSでなければ実現できないものだけ: ファイル選択・保存先選択 (`dialog.showOpenDialog` / `dialog.showSaveDialog`) などのOSファイルピッカー

## Editor Specific Rules

### Math

数式編集は、見た目の美しさと入力のしやすさを両立する。

- 数式は `mathInline` として扱い、`\\` を含むTeXも本文行の高さを優先して表示する
- 短い数式は本文行のリズムを崩さない
- 編集中の数式はフォーカス状態を明確にする
- TeX入力欄は必要な時だけ表示する
- 数式エラーは派手にせず、該当箇所の近くに控えめに出す
- 教材タイトルの `$…$` は表示面でのみ数式として描画する。保存値は入力どおりの文字列で、描画のためにデータを書き換えない
- 対になっていない `$`・散文 (`セール $100 と $200`)・元の文字列を復元できない書き方 (`$ x^2 $` や `$$…$$`) は数式にせず、タイトル全体を素の文字列として表示する。`$` を記号として使いたい場合は、対にならないよう 1 つだけ書けばそのまま表示される
- タイトルはツールチップ・`aria-label`・ファイル名・検索など素のテキストしか置けない面では生の文字列のままにする
- 数式の markup は `renderMathHtml` (`features/rendering/adapters/math-html.ts`) の出口で許可リスト方式に無害化する。TeX から HTML を作って `dangerouslySetInnerHTML` へ流す経路をここ以外に作らない
- 危険な文字 (`<` `>` `&`) を含む TeX を数式にしない、という入口フィルタは足さない。これらはごく普通の数学 (`$a<b$`、`\begin{aligned}…&…\end{aligned}`) で出るので、防御ではなく機能破壊になる

### Figures And Images

図解、グラフ、画像（いずれもオーバーレイのシェイプ）は教材の一部として扱う。

- キャプションは控えめな文字サイズにする
- 選択中だけリサイズハンドルや整列ガイドを表示する
- 図形モードで図形を掴めるのは「描かれているところ」だけにする。図形のDOMは外接矩形（変形の基準箱）だが、それを当たり判定にはしない。円弧は元の円まるごとが基準箱なので、弧の内側の空白は空白として扱う
- 図形内の文字・吹き出し・表セルの編集中は、上部ツールバーの文字書式をその編集対象へ適用する。サイズ入力などへフォーカスが移っても選択範囲を維持し、文字図形全体の選択と文字の範囲選択を区別する
- 図形・表の貼り付けは、図形と画像資産をSigmaDocへ同じ操作で確定してから選択を移す。Cmd/Ctrlを離す、一時的な図形モードを抜ける、教材を再表示する操作で貼り付け結果が消えないようにする
- 図形モード中でも、図形の外側で本文に触れたら本文へ戻す。クリックはその位置のキャレット、図形を1つも囲まなかったドラッグはその範囲の文字選択として引き継ぐ。紙の余白（本文が無いところ）での空振りマーキーは図形モードに留まる
- 本文のドラッグ選択は、左右の余白へ出ても近い行の端へ伸ばす。余白から選び始めた場合は本文へ入った行を起点にし、開始位置まで戻せば選択を畳む。内部の編集面の分割によって操作結果を変えず、ドラッグ中の表示・離した後の選択・次の入力の置換範囲を一致させる
- 通常の左ボタンを押したまま本文上を動かす操作は、キャレットや既存の選択がある場合も本文の範囲選択として扱う。連続クリックの後も追跡を続ける。Cmd/Ctrlによる図形操作、専用のブロックグリップ、入力欄・ボタン・数式の編集操作は各操作の経路を保つ
- 図や画像の境界線は薄くする
- 本文アンカーは錨アイコンではなく、「ここから下がこの図」と読める境界線として表示する。線は紐付く本文行の**直後**（最終行はブロック下端）に引き、段落の途中を横切らせない。両端は下向きの爪、図までは破線の引き出し線でつなぐ
- 本文のブロックグリップ（左ガターの ⋮⋮）は「掴んで動かす」もの。押して数 px 動いたらドラッグ、動かさず離したらクリック（選択とメニュー）。グリップは掴む単位ごとに出す — 箱・引用・段組・問題エリアの中の段落、リストは 1 項目ずつ（Enter で分かれた項目が別ブロック、Shift+Enter の継続行は同じ項目）。左ガター・段間でもポインタが居るレーンと高さの最も内側の単位へ出し、問題・箱・段組そのものは最初の行より上の上端帯からだけ掴める
- ページを跨ぐブロックは同じSigmaDocのIDを保ち、各ページで見えている範囲にグリップ・選択枠・ドロップ判定を対応させる。元ページで隠れた部分やページ間の空白を選択枠で覆わない。下余白つまみは本文の実際の末尾にだけ出し、続きの表示枠の端を文書の挿入境界として扱わない
- 改ページ先の本文は、外側の余白だけを元ブロックの計測原点へ合わせ、内部の段落・コード・入れ子枠の組版を保つ。Enterや貼り付けで増えた段落も、元の文書コンテナへまとめて反映する
- ブロックのドラッグ中は本文を 1px も動かさない。掴んだ単位の写し（ゴースト）がポインタに追従し、元のブロックは紙色のベールで薄くし、落とし先は線で示す — 前後なら横線、横並び（段組化・段の追加）なら縦線。線は挿入線と同じアクセント色で、端に丸を付ける。Esc でキャンセル、文書へ書くのは離した 1 回だけ（undo も 1 手）
- 落とし先はブロックの左右端の帯（幅の 18%、20〜56px）で横並びになる。問題・段組そのものは横並びにできず、その帯でも前後の横線に倒す。段組の段は最大 4。空いた段は詰め、1 段になった段組は解く
- グリップと下余白線は、部分段組を含め常にホバー中の 1 単位だけへ表示する。文字そのものではなく、左ガター・段間を含むそのレーンの行高に入れば操作できる。外側の段を先に解決してからその段の入れ子だけへ降り、兄弟段の同じ高さにある入れ子へ飛ばない。入れ子リストの行から左へ移動するときは各インデント帯でも最深の項目を保ち、親項目へ跳ばない。リスト項目のグリップと下余白線はマーカー（•・○・番号）の左、つまり項目が属するリスト要素の左端を基準に出し、マーカーに重ねない。親項目の下余白線は親の本文行の下（入れ子リストの手前）に出し、リスト全体の下には出さない。段間と段の左ガターは右側の段へ帰属し、箇条書きの下余白線・実余白は各項目の継続行を含む本文下端（入れ子リストの手前）へ一度だけ出す。ポインタが静止したまま Enter・Backspace・貼り付け・入力で本文寸法が変わっても、次の描画で同じ辺へ追従させる
- 自動改ページ・改段では、本文を実測した行境界で分割し、現在のページ・段の残り高さから流す。「次のページならブロック全体が収まる」だけを理由に丸ごと送らない。枠付き問題も同じ本文フローを使う。手動の改ページ・改段、明示的なまとめ指定、図などの不可分な内容は維持する。部分段組の続きは、その列のまま次ページへ送る
- 囲み枠（box）は問題・区切り線・段組・別の枠を含む任意の文書ブロックを包める。内側の3点ボタンは、その枠自身の設定を開く。入れ子の問題も番号・枠・解答欄の予約高・出力対象の設定を保つ
- 囲み枠（box）が祖先にある位置では手動改ページ・外側への改段を追加しない。入れ子の枠・コード・引用・問題内でも同じ規則を適用する。枠内の局所段組にも手動改段を追加しない。操作メニューは枠外と同じ配置・順序を使い、引用内の段組化など実行できない候補は表示しない
- 手動改ページより前の行を削除・追加しても、ページ数が変わらない限り、後続ページの本文開始位置は動かさない。文書先頭や手動改ページ直後に本文がなく、空段落だけがある位置では、新たな改ページ・改段を挿入できない。既存の境界の解除は引き続き可能にする
- 文書先頭の本文を削除して空段落だけになった場合は、本文より前に残った手動改ページを同じ編集で解除する。判定は編集面の断片ではなく文書全体で行い、途中の有効な境界は維持する
- 本文編集では段落末尾・明示的な行内改行ともに `↵` を表示する。編集記号は本文の寸法を変えず、保存・コピー・印刷には含めない
- 部分段組の列は独立して編集する。左列末尾のEnterは左列を伸ばし、右列へ送らない。列境界は共通ガイドでリサイズし、幅が0になった列は隣へ読み順で結合する。枠内外とも複数列を持つ局所段組内には手動改段・改ページを追加しない
- 段間の線は表の罫線と同じ線種・線幅メニューと色パレットで設定する。ページ設定の線は全ページ共通、部分段組の線は枠内外ともブロックごとに適用する。線なし・実線・破線・点線・二重線を選べ、設定画面にプレビューを置く。線は本文の幅・高さや列所属を変えず、編集・Viewer・PDFに同じ設定を描画する。リサイズ用のガイドは編集専用のままにする。
- 部分段組は枠内外とも独立したGrid列で描画し、列幅・段間・境界位置は `rendering/core/independent-column-layout.ts`、境界のドラッグは `editor/layout-column-resize.ts` を共有する。React／Tiptap／静的出力のアダプタで別の列幅計算やCSS multicolによる再配分を行わない。Tiptapの `layoutColumn` は列所属を表す編集用の投影で、SigmaDocには保存しない。列所属のない旧box段組だけを互換境界で読み替え、明示された列所属は再配分しない
- 列内の空白をクリックしたときも横位置から列を先に選び、その列内の最寄りの本文へキャレットを置く。低い列の空白を、背の高い隣の列へ渡さない。改段マーカーと幅のドラッグプレビューは編集専用の表示で、本文の高さや保存内容に混ぜない
- ⌥⇧↑/↓ はキャレットのあるブロック（グリップで選んでいればその選択）を前後の兄弟と入れ替える。入れ物の端では外へ出る
- 本文アンカーはアイコンだけのグリップを常時表示する。境界線、図までの引き出し線、接続先本文の面表示はグリップのホバー・フォーカス・ドラッグ中だけ表示する。接続状態の説明もグリップのホバー・キーボードフォーカス時だけツールチップで表示し、常設しない
- アンカー線そのものは `pointer-events: none` にし、掴めるのは中央のグリップだけにする（本文のクリックを線が食わないようにする）
- アンカーのドラッグはブロック単位でスナップし、ドラッグ中は紐付け先の本文ブロックを面で示す。本文に紐付いていない図形は灰色の破線と「本文に未接続」で区別する
- アンカーUIは絶対配置で、本文の高さや改ページを変えない
- 空の図形ブロックはアイコン中心のプレースホルダーにする
- グラフの詳細設定は右インスペクタへ常設せず、右クリックの「グラフの設定…」から、グラフの横に寄る非モーダルの設定パネル（グリッドの既定幅620px、空き幅に応じて300pxまで縮小）を開く。パネルはグラフを覆わない位置（右→左→下の順）に自動配置し、ヘッダーを掴んで移動できる。編集結果をリアルタイムに観察できることが目的なので、backdrop は敷かず、原点指定・塗りつぶし・トリミングを開始してもパネルは閉じない（実行中は該当ボタンを `aria-pressed` にし、パネル冒頭の `role="status"` 行で次の操作を案内する）
- 関数と塗りつぶしの補助操作は、グラフ本体のホバーへ重ねず、グラフ設定パネル内の各項目をホバーした時に現れる `⋯` へ集約する。`⋯` 自体のホバーで項目の横へメニューを展開し、塗り方は現在値と見本を示すドロップダウンで選べるようにする
- グラフ設定パネル内を操作している間は対象グラフの選択を維持し、本文・空白・別図形へフォーカスまたは選択が移ったらパネルを閉じる
- グラフのダブルクリックは、画像と同じくトリミングを開始する
- グラフのトリミング、原点指定、塗りつぶしなどの直接操作は右クリックメニューからも開始できるようにする
- 3D教材も2Dグラフと同じ挿入・選択・浮動設定パネルの文法を使う。ダブルクリックするとページ上の表示枠そのものがlive viewportになり、立体をクリックすると局所軸と軸間の円弧矢印が出る。円弧ドラッグは回転（Shift中は15度刻み）、軸中央ドラッグは平行移動、正方向の軸端ドラッグはその局所軸だけの拡縮、余白ドラッグは視点、ホイールはcameraの拡大縮小とする
- 3D設定パネルはbackdropを持たず、対象の横へ置き、ドラッグで移動できる。パネル内には別のviewportを置かず、数式・立体・共通部分・表示設定などの編集だけを担う
- 2D・3Dのパラメータ、折りたたみセクション、要素カードのグリッド、追加ボタンは共通部品を使う。カードは内容の高さに合わせて配置し、追加ボタンだけで高い空行を作らない。狭いパネルでは1列にする
- パラメータの再生値は表示用の状態とし、スライダーと数値表示を同じ値から描く。再生中の毎フレームは保存せず、停止・パネルを閉じるときに最後の値を確定する。2Dの評価用の数値置換は派生投影に限り、SigmaDocの式とパラメータ定義を残す
- 2D・3Dのパラメータ欄に共通の「動画で書き出す」を置き、進捗と保存結果を同じ場所に表示する。「ページ上でも動かす」の指定を優先し、未指定なら範囲のある全パラメータを各自の時計で再生する。動画はSigmaDocからの一時的な投影とし、式や保存値を変更しない。MP4を優先し、対応しない環境ではWebMを使う
- 3D教材の表示枠は立体を覗く窓として扱う。枠の縦横比を自由に変えても立体の比率は変形させず、cameraのaspectと表示範囲を追従させる。静止previewも枠いっぱいに切り抜いて表示する
- 3D教材の関数入力は2Dグラフと同じ `MathExpressionInput` とMathLiveを使い、表示用TeXを評価式へ変換してSigmaDocへ保存する
- 立体、共通部分、parameter、数式ラベルは折りたたみセクションで段階的に開示する。切断面の専用UIは置かない。平面との切り口は共通部分のメンバーに平面を混ぜて表す
- 3D教材の数式エラーは入力値を消さず、viewport近くに診断を表示する。重い再計算中も既存の静止previewを保持し、空白へ置き換えない
- 点を置いて描く作図ツール（曲線・折れ線・3点円弧）は、置いた点をマーカーで示し、次の操作（点を置く／確定する／1点戻す／取り消す）を画面下部の `role="status"` のピルで常時案内する。折れ線を閉じられる状態では最初の点のマーカーを拡大して当たり判定を可視化する
- 確定後の線の制御点は白丸の頂点ハンドル（位置を動かすもの）で表す。黄◆はパラメータ調整の語彙なので流用しない。セグメント中点の破線ハンドルで点を追加し、頂点の Alt+クリックで削除する。先頭の点は図形の原点なので削除できない

### Block Operations

ブロック操作は、本文の邪魔をしない位置に置く。

- ドラッグハンドル
- 複製
- 削除
- 上下移動
- ブロック種別変更

これらはブロック選択時またはホバー時に表示し、常時表示は避ける。

- boxのタイトルは本文上で直接編集し、スタイル、枠、角、タイトル位置、パディングはホバー時の⋯メニューから開く中央ダイアログに集約する
- boxの詳細設定は右インスペクタへ重複して表示しない

### Box Frames And Appearance Settings

角丸・枠線・背景・タイトル装飾は組み合わせた状態で成立させる。外枠だけに角丸を指定して完了としない。

- タイトル帯、塗り、内側の二重罫、ノート枠も外枠の形に沿わせる。角丸の内側の半径は、枠線の太さや内側への距離を考慮し、四隅に四角い塗り残し・罫線・隙間を作らない
- 箱全体を一律にクリップして、枠にまたがるタイトルや編集用ボタンまで切らない。各装飾の責務に合わせて形を整え、入れ子の箱へ親の装飾や配色を漏らさない
- 切り欠きなど独自の角形状を持つスタイルでは、その形状を保つ。結果に反映されない角丸設定を操作可能なまま表示しない
- 見た目の設定ダイアログには、タイトル・数式・現在値を反映する即時プレビューを置く。本文と同じ描画規則を使い、スタイル一覧の縮小見本も余白やタイトルを含む全体を表示する
- スタイル一覧は必要時に展開し、普段の調整項目を押し下げすぎない。長いタイトル、大きな余白、狭い画面でもプレビューと操作欄が重なったり欠けたりしないようにする
- 枠の描画を変更したら、全スタイルを実際に描画し、Electronのスクリーンショットを並べて確認する。標準、最小・中間・最大の角丸、太い枠線、色付き背景、タイトル位置を含め、崩れを直してから完了とする
- 空の本文、長いタイトル、入れ子、保存・再読込、印刷表示も確認する。CSSの宣言値やビルド成功だけで、角が正しく描かれたと判断しない

全スタイルの描画・スクリーンショット・保存後の確認は、[Electronのboxデザイン検証](../apps/desktop/tests/electron/box-design.spec.ts)を基準に拡張する。

## Empty And Error States

空状態やエラー状態でも、説明過多にしない。

- まずアイコンで状態を示す
- 短い見出しを置く
- 必要な場合だけ1文の補足を付ける
- 次に取るべき操作を1つだけ提示する

例:

```text
[image icon]
画像がありません
ドラッグして追加
```

## Accessibility

ミニマルな見た目でも、操作可能性を犠牲にしない。

- アイコンボタンにはアクセシブルな名前を付ける
- キーボードフォーカスを明確に表示する
- コントラストを十分に確保する
- 色だけで状態を伝えない
- 破壊的操作は取り消し可能にする

## Print And PDF

PDF出力は、アプリUIよりも教材としての読みやすさを優先する。

- 白背景、黒文字を基本にする
- 余白、行間、数式サイズを安定させる
- 不要なUI要素は出力しない
- 問題、コメント、解答などの意味単位を崩さない
- 図とキャプションは可能な限り同一ページに収める

PDF上の装飾も最小限にし、教材本文、数式、図解が読みやすいことを最優先する。

## Do And Do Not

### Do

- とにかく直感的でシンプルにする
- 白、黒、グレー基調で設計する
- グレーで面、階層、状態を丁寧に表現する
- アイコンで直感的に操作できるようにする
- ツールチップで最小限の補助を出す
- 余白と境界線で構造を作る
- 固定のスペーシングトークンと共通レイアウトコンポーネントを使う
- 編集対象を最も目立たせる
- 状態変化を明確にする

### Do Not

- 見た目の凝った表現を操作の分かりやすさより優先しない
- 説明文を画面に並べすぎない
- 派手な色やグラデーションを主役にしない
- 影や角丸で装飾しすぎない
- カードを入れ子にしない
- 任意の`margin`、`padding`、`gap`を画面ごとに増やさない
- アイコンだけで危険な操作を即実行しない
- PDF出力にアプリUIの見た目を持ち込まない
- OSが描画するUI (ネイティブの `<select>`、`window.confirm`、カラーパネル、日付ピッカー) をアプリの操作面にしない

## Design Review Checklist

UIを追加または変更する時は、次を確認する。

- 白、黒、グレー基調から外れていないか
- グレーの濃淡で面、階層、状態が整理されているか
- 初見でも直感的に操作できるか
- シンプルさを損なう要素が増えていないか
- 教材本文または編集対象が主役になっているか
- 読み込み中にShimmerが表示され、現在の状態を理解できるか
- 説明文なしでも主要操作を理解できるか
- アイコン、ツールチップ、状態表示が揃っているか
- 画面の主役が1つに絞られ、余白によって自然に強調されているか
- 角丸、境界線、アイコン位置、文字位置が同種の要素で揃っているか
- アクセントカラーや影を必要以上に広い面積へ使っていないか
- 余白がスペーシングスケールの値に限定されているか
- `Stack`、`Inline`、`Inset`、`Center`、`Grid`で配置と余白を管理しているか
- 選択、確認、色や日付の入力が、OSではなくアプリ内のUIで完結しているか
- 設定ダイアログの選択ボタン、数値欄、スライダーにブラウザ標準の見た目が残っていないか
- 角丸と装飾の組み合わせを全スタイルの実画面で確認し、四隅の塗り残しや見本の欠けを解消したか
- 長い文字列がはみ出さないか
- キーボード操作とフォーカス表示が成立しているか
- PDF出力時に不要なUI表現が混ざらないか
- 教材として読みやすい余白、行間、数式サイズになっているか

### Overlayの編集座標と操作UI

- 図形の保存位置と画像の移動・リサイズ・トリミングはSigmaDocの座標で扱い、用紙外の座標も編集できる。本文上でのポインター振り分けと印刷の用紙範囲は、それぞれの境界で扱う。
- 表のフローティングツールバーなど編集専用の操作UIは、図形や用紙の子座標面から画面上の独立したポータルへ出す。移動範囲を表の幅・高さに制限せず、画面の可視範囲に収める。ズームで操作UI自体を縮小せず、スクロール・リサイズに追従する。
- コメント欄は用紙端ではなく、overlayのはみ出し量を含む編集範囲の外側へ置き、用紙外の画像や図形を覆わない。
- 操作UIのドラッグは専用グリップが所有し、図形の移動や本文選択へ伝播させない。編集終了時はポータルと監視処理を破棄する。
